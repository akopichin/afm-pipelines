# Architecture images in plan approval

Use this toolkit during ordinary planning. It is independent of the optional
grooming workshop: there is no extra choice, browser session, readiness click or
approval. Node.js 18+ is sufficient; the package freezes its layout engine,
WebAssembly rasterizer and Cyrillic fonts. It renders offline without npm install,
Chrome, provider calls or system font dependencies in the target project.

## Describe the actual change

Write `c4.json` in the absolute plan stage directory using schema version 1 and a
positive `revision`. `c4-example.json` is a **synthetic** example with C3 and C4
views; replace its facts and references with the actual project and approved scope.

- `title`: the task; `primary_view`: the ID shown inline; `views`: 1–6 focused views.
- Each view has `id`, `level` (2, 3 or 4), `title`, `scope`, its own `what` and
  `why`, `nodes` and `relations`. Use lowercase ASCII IDs with hyphens.
- C2 shows containers and stores inside one system. C3 shows components inside
  one container. C4 shows code symbols inside one component. Name that boundary
  in `scope`; never mix these levels inside it. Supporting external nodes use
  `external: true` and stay outside the boundary.
- Each node has a stable `id` and `before`/`after` objects with `name`, `type`,
  `technology` and a short `description`. Types: `person`, `system`, `container`,
  `store`, `component`, `code`. People need no technology. Omit `before` for an
  addition and `after` for a deletion. Existing nodes need real `source_refs`
  (`path:line` or a real symbol); changed nodes need `task_ids` from dev-plan.md.
- Relations have stable `id`, `from`, `to`, and `before`/`after` objects with
  directional `label` and communication `technology`. Endpoints must exist in
  the corresponding version. Use dependency/call directions consistently.

Show only affected architecture and enough existing context to understand it.
Use C3 for component changes, C2 for system/container boundaries, and C4 only
when concrete code structure clarifies the proposal. Explain an omitted requested
level in the plan; do not fabricate classes or architectural changes for it.
Limit each view to eight nodes and twelve relationships. Split a crowded view
instead of producing unreadably small text. Before/after images share one layout.
Changes use both color and labels: gray existing, amber changed, green added, red
removed. A missing node leaves its position empty in that version.

For a change with no useful architectural diagram (such as a spelling correction),
use `views: []` and a concrete `skip_reason`; this is visible in the approval
question and checked by the plan reviewer.

## Render and show the plan

Finish `dev-plan.md` and `project.json` before rendering. Keep generated image
links in the separate presentation, so they do not create a circular plan hash.

```sh
TOOL="$(dirname "$AFM_STAGE_DIR")/bootstrap/planning/c4.mjs"
node "$TOOL" render --session "$AFM_STAGE_DIR" \
  --root "$(git rev-parse --show-toplevel)"
```

This writes `c4-approval.md`, `c4-manifest.json`, and immutable, content-addressed
PNGs under `artifacts/`. The default `compact` presentation embeds the primary
**After** image and provides a small table of **Before / After** links for all
levels. Clicking an image opens the full PNG. `--presentation all` additionally
embeds each remaining image. Do not use `<details>`: the current AFM Markdown
renderer escapes HTML and does not provide those disclosures in questions.

Include the **unchanged** contents of `c4-approval.md` in the one existing AFM
approval question, together with the complete plan, checks and tradeoffs. Use
ordinary AFM option/answer handling. If an explicitly requested grooming workshop
is active, use its exact approval label in that same question.

After AFM creates the real question file, bind it:

```sh
node "$TOOL" bind-question --session "$AFM_STAGE_DIR" \
  --question "<absolute AFM question.json from this stage>"
```

Wait for the actual human answer and record question/answer paths in `approval.md`
as usual. Binding a question is not approval; the normal approval protocol and
independent plan review remain mandatory. The helper checks that the actual
question contains this exact presentation. Never fabricate a question file to
satisfy this check.

```sh
node "$TOOL" verify --session "$AFM_STAGE_DIR"
```

Verification checks source identity, plan/project bytes, the model, presentation,
every published artifact and the bound question. The reviewer separately checks
the real answer and that the nodes, source references and task IDs describe the
actual change. A model or plan change requires rendering again and binding the
new approval question; increment `revision` for a changed proposal. Old PNGs,
model snapshots and question receipts remain available for earlier discussions.

Missing renderer files or failed rendering must be reported and fixed before
asking approval; do not substitute an unrelated image or silently omit the view.
